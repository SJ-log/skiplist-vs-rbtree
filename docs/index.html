Skip List vs rbtree

여러 스레드가 동시에 쓰면, 누가 더 잘 버틸까?

커널의 rbtree는 보통 트리 전체에 락 하나를 건다. 우리는 노드마다 락을 거는 skip list를 커널 모듈로 직접 만들고, 스레드 수를 늘려 가며 누가 더 많이 처리하는지 잰다.

구현 5개 + 측정 틀 1개, 전부 커널 모듈

락이 덮는 범위가 성능을 정한다

여러 스레드가 정렬된 키 집합 하나에 동시에 넣고, 찾고, 지운다. 이때 락을 어디까지 거느냐에 따라 스레드를 늘렸을 때 처리량이 달라진다. 이걸 커널 안에서 직접 만들어 재는 게 이 프로젝트다.

rbtree: 트리 전체에 락 1개

키 45를 넣으면 부모(40)와 삼촌(25)이 모두 빨강이라 25·30·40의 색이 바뀐다. 큰 트리에서는 이 재색칠과 회전이 뿌리까지 올라갈 수 있다. 어디가 바뀔지 미리 모르니 보통 트리 전체에 락 하나를 건다.

커널 곳곳에서 쓴다: CFS 런큐, hrtimer, 예전의 VMA 관리.

skip list: 바뀌는 노드만 잠근다

키 25를 2층짜리로 넣을 때 바뀌는 포인터는 바로 앞 노드인 19(L1)와 22(L0)뿐이다. 그 두 노드만 잠그면 7이나 31 근처에서 일하는 스레드는 기다리지 않는다.

회전 같은 재균형이 없어서 수정 범위가 좁다. 이게 동시성에서의 장점이다.

스레드 4개 · 측정 중

개념을 보여 주는 모형이다. 연산 시간은 임의로 정했고, skip list는 포인터를 더 따라가므로 한 번이 조금 더 오래 걸리게 했다. 그래서 스레드 1개에서는 rbtree가 앞선다. 실제 수치는 실험으로 잰다.

구현 5개를 같은 측정 틀에서 잰다

발표의 줄거리는 세 정거장이다. 전부 잠그는 rbtree, 읽기만 락 없이 하는 xarray, 쓰기까지 동시에 하는 skip list v2. 나머지 둘은 공정한 비교를 위한 기준이다.

rbtree + 락전부 잠금
xarray읽기만 락 없음
skip list v2쓰기도 동시
구현읽기끼리 동시쓰기끼리 동시이 비교에서 맡는 역할담당
rbtree + spinlock안 됨안 됨기준선. 커널이 보통 쓰는 방식A
rbtree + rwlock됨안 됨탐색 위주 조건에서 공정한 기준A

v3(RCU로 탐색하는 skip list)는 여유가 있을 때만 D가 시도한다.

xarray와 스레드 수 1·2·4는 제안이다. 강성준의 VM은 커널 5.4, vCPU 4개다. 5.4에는 maple tree(6.1부터)가 없어서 xarray로 바꾸고, 스레드는 4개까지만 재는 안이다. 팀원 VM도 같은지 확인하고 첫 회의에서 확정한다.

v1이 왜 필요한가

속도 차이가 자료구조 때문인지 락 때문인지 나눠서 말하기 위해서다.

rbtree↔v1락은 같고 구조만 다름 → 자료구조 효과
v1↔v2구조는 같고 락만 다름 → 락 효과

xarray를 왜 넣었나

커널도 읽기가 몰리는 곳에서는 락을 피한다. 페이지 캐시에 쓰는 xarray는 읽기를 RCU로 락 없이 한다. 그런데 xarray도 쓰기는 락 하나로 줄을 선다.

그래서 "옛날 방식인 rbtree만 이긴 것 아니냐"는 질문을 막고, v2의 차별점을 쓰기도 동시에 된다로 좁힐 수 있다.

원래는 maple tree를 넣으려 했다. 커널이 6.1부터 메모리 영역(VMA) 관리를 rbtree에서 maple tree로 바꿨기 때문이다. 커널 5.4에는 없어서 락 구조가 같은 xarray로 바꿨고, maple tree는 관련 연구로만 소개한다.

주의할 점: xarray는 키가 촘촘한 정수일 때 트리가 낮아서 1스레드 속도부터 빠를 수 있다. 그래서 절대값과 함께, 스레드를 늘렸을 때 얼마나 오르는지를 본다.

증명하고 싶은 것: 쓰기가 섞이면 v2만 계속 오른다

"skip list가 무조건 빠르다"가 아니다. 어떤 조건에서 왜 이기고 왜 지는지를 데이터로 설명하는 게 목표다. 아래 그래프는 가설을 그림으로 옮긴 예상 모양이다.

쓰기가 절반이면 v2만 계속 오른다

예상 · 실측 아님

비율은 탐색 · 삽입 · 삭제 순서다.

  1. 1
    확장성스레드를 늘릴수록 v2 처리량이 오른다. rbtree + spinlock은 거의 평평하다.
  2. 2
    쓰기 동시성쓰기 비율이 높을수록 v2와 xarray의 차이가 벌어진다. 왼쪽 버튼으로 비율을 바꿔 보면 보인다.
  3. 3
    범위 탐색스캔이 도는 동안 rbtree는 쓰기가 멈추고, v2는 계속 쓴다.
  4. 4
    정직한 예상스레드 1개에서는 rbtree가 이긴다. skip list가 포인터를 더 많이 따라가기 때문이다.

가설이 맞았다고 말할 기준

쓰기가 섞인 조건에서 스레드가 늘수록 v2가 rbtree와 xarray를 앞서면 성립한다. 지는 조건이 나와도 그것 역시 결과다. 이동 노드 수와 재시도 횟수로 이유를 붙인다.

가설 3 · 스캔 중에도 쓸 수 있나

스캔 스레드 하나가 맨 아래층을 훑는 동안, 쓰기 스레드 셋이 빈 자리(점선)에 키를 넣으려 한다.

rbtree는 스캔이 락을 쥐고 있어서 쓰기가 스캔이 끝날 때까지 기다린다. rwlock이어도 스캔이 읽기 락을 잡으므로 쓰기는 막힌다.

가설 4 · 1스레드에서 왜 지나

키 하나를 찾을 때 따라가는 노드 수의 이론 기댓값이다. 대략적인 값이고, skip list는 p = 1/2 기준이다.

원소 1만 개
rbtree약 13칸
skip list약 27칸
원소 10만 개
rbtree약 17칸
skip list약 33칸
원소 100만 개
rbtree약 20칸
skip list약 40칸

skip list는 평균 2배쯤 더 따라간다. 노드마다 캐시 미스가 날 수 있어서, 스레드가 1개면 이 차이가 그대로 시간 차이가 된다. 실제 값은 이동 노드 수 카운터로 잰다.

실험: 변수 3개를 조합하고, 범위 탐색은 따로 잰다

모든 구현을 같은 VM, 같은 조건에서 돌린다. VM이라 값이 흔들리므로 조건마다 5번 반복해 평균과 편차를 낸다.

원소 수

1만10만100만

스레드 수

124

실험 VM의 vCPU가 4개라 4까지. 8개로 늘릴 수 있으면 8도 잰다

작업 비율 (탐색·삽입·삭제)

100·0·090·5·550·25·250·50·50
36조건 (3 × 3 × 4)

약 45분한 번에 3초씩 돌릴 때
+1범위 탐색 실험: 스캔 1 + 쓰기 1·2·3, 스캔 길이 100·1,000

재는 값

  • 처리량 (ops/s): 모든 그래프의 주인공
  • 평균 지연 (ns/연산)
  • 이동 노드 수 (연산당): 1스레드 분석용 카운터
  • 재시도 횟수: v2의 검증 실패. 경합이 얼마나 심한지 보여 준다
  • 노드당 메모리 (선택): 노드별 락과 포인터 배열의 비용

카운터는 컴파일 옵션으로 켠다. 처리량을 잴 때는 끈다.

처음 계획에서 바꾼 점

  • "삽입만" 조건을 뺐다. 키 범위가 정해져 있어 금방 다 차고, 그 뒤 삽입은 "이미 있음"으로 실패한다. 결국 탐색을 재게 된다.
  • 삽입과 삭제를 같은 비율로 섞는다. 원소 수가 일정하게 유지되고, 과제 요건인 삭제 성능도 함께 잰다.
  • 범위 탐색을 넣었다. 과제 요건인 순회(traverse)를 재고, 락 범위 차이가 가장 크게 드러난다.
  • 스레드는 4개까지 잰다 (제안). 8개까지 늘리려 했지만 실험 VM의 vCPU가 4개다. vCPU를 8개로 늘릴 수 있으면 8도 잰다.
  • maple tree 대신 xarray를 쓴다 (제안). maple tree는 커널 6.1부터 있는데 실험 커널은 5.4다.

구조: 측정 틀 하나에 구현을 끼운다

모듈 하나는 측정 틀(harness)과 구현 하나를 묶은 것이다. 예를 들어 bench_rb.ko는 harness.o와 rbtree_lock.o로 만든다. 공통 함수 묶음 ds_ops만 맞추면 각자 따로 개발하고 나중에 그대로 끼운다.

결과는 CSV로 모으고, D가 그래프로 만든다.

ds_ops: range 한 줄을 추가한다

struct ds_ops {
	const char *name;
	int  (*init)(void);
	int  (*insert)(u64 key);        /* 0 | -EEXIST | -ENOMEM */
	bool (*search)(u64 key);
	int  (*remove)(u64 key);        /* 0 | -ENOENT */
	u64  (*range)(u64 lo, u64 hi);  /* 추가: [lo, hi] 안의 키 개수 */
	void (*destroy)(void);
};

반환값 규칙은 제안이다. 첫 회의에서 확정한다.

공부할 것: 모두 같이 7가지, 그다음 자기 노선

공통 7가지는 모두가 설명할 수 있어야 한다. 짝이 빠져도 그 부분을 대신 설명할 수 있게 하는 게 기준이다.

모두 공통

  1. 커널 모듈 기초module_init/exit, insmod · rmmod, pr_info와 dmesg, Makefile의 obj-m. 4주차 과제 복습이면 충분하다.
  2. 커널 스레드kthread_run, kthread_stop, completion으로 기다리기. LKD 3장.
  3. 스핀락과 rwlock스핀락을 쥔 채로 잠들면 안 되는 이유. LKD 9~10장.
  4. 커널 rbtree API내 구조체에 rb_node 넣기, rb_link_node · rb_insert_color · rb_erase. Documentation/core-api/rbtree.rst, LKD 6장.
  5. skip list 원리층 수는 동전 던지기로 정한다. 위층에서 건너뛰고 넘치면 내려간다. 평균 O(log n). Pugh 1990.
  6. 동시성 기본경쟁 조건, 교착 상태, 락을 잡는 순서. READ_ONCE가 왜 필요한지 정도까지.
  7. Git PR 흐름feat/ 브랜치 → PR → 강성준이 확인·approve → merge. 체크리스트는 PR 템플릿에 있다.

역할: 각자 자기 노선 하나

사람마다 색이 곧 자기 구현의 색이다. 모든 PR은 강성준이 확인하고, 강성준의 PR은 이은찬이 확인한다. 백업 짝(강성준 ↔ 이은찬, 이우신 ↔ 종주원)은 서로의 파트를 설명할 수 있게 유지한다.

공통 규칙과 함정

커널 모듈은 실수 하나에 VM이 멈춘다. 아래는 모두가 지킨다.

Git

  • main에 직접 push하지 않는다
  • 브랜치는 feat/harness, feat/sl-v2, feat/xarray처럼
  • PR → 강성준이 확인·approve → merge (강성준의 PR은 이은찬)
  • 빌드 산출물(*.o, *.ko)은 커밋하지 않는다
  • 커밋 메시지는 영역: 무엇을

커널 모듈 안전

  • 실험 전에 VM 스냅샷을 떠 둔다
  • 다른 터미널에 dmesg -w를 띄운다
  • insmod 전에 sync
  • Oops나 BUG가 뜨면 재부팅한다
  • 작은 nkeys부터 단계적으로 늘린다

코드 함정

  • 스핀락 안에서 kmalloc(GFP_KERNEL) 금지. 락을 잡기 전에 할당한다
  • 삭제한 노드를 바로 kfree하지 않는다. 지연 해제 목록에 모았다가 destroy 때 해제한다
  • 반복문 안에서 pr_info 금지. 요약 한 줄만 출력한다
  • 스레드별 카운터는 ____cacheline_aligned로 false sharing을 막는다
  • 락은 항상 아래층 → 위층 순서로 잡는다
